### 🎯 **Objetivo del Trabajo**

Evaluar la aplicación integrada de los contenidos de Metodología de Sistemas II mediante el análisis y mejora de un sistema de software. El trabajo debe evidenciar la diferencia entre calidad externa e interna, identificar deuda técnica, reconocer code smells, aplicar principios SOLID y Clean Code, ejecutar refactorings seguros y realizar una revisión técnica profesional.

- **Calidad interna y externa:** distinguir lo que el usuario percibe del funcionamiento del sistema y lo que el equipo técnico debe cuidar en su estructura interna.
- **Deuda técnica y code smells:** detectar problemas de diseño que elevan el costo del cambio.
- **SOLID y Clean Code:** aplicar criterios de diseño orientados a mantenibilidad, claridad y bajo acoplamiento.
- **Refactoring seguro:** mejorar el diseño interno sin alterar negativamente el comportamiento externo.
- **Code review:** revisar el código con checklist, criterios técnicos y feedback profesional.

---

### 📚 **Tema y Marco Referencial**

El TPI parte de un sistema o módulo simple ya existente, o de un prototipo construido por el equipo, que será analizado y mejorado. La complejidad esperada no está en desarrollar muchas funcionalidades, sino en justificar técnicamente cómo se mejora la calidad del software.

**Caso sugerido:** Sistema de Gestión de Solicitudes Académicas. El sistema permite registrar solicitudes de estudiantes, clasificarlas por tipo, prioridad y estado, asignar responsables, consultar solicitudes y generar reportes simples.

También puede utilizarse otro dominio equivalente, por ejemplo: gestión de incidencias, turnos, reservas, pedidos, tareas o un módulo de un proyecto desarrollado previamente, siempre que permita aplicar diagnóstico de calidad, refactoring y code review.

---

### 🧩 **Etapas obligatorias**

1. **Selección y descripción del sistema base:** dominio, alcance, actores, funcionalidades, tecnología utilizada, repositorio y evidencia de funcionamiento.
2. **Calidad externa vs. calidad interna:** análisis de qué funciona desde la mirada del usuario y qué problemas existen en la estructura interna del sistema.
3. **Deuda técnica y code smells:** identificación de al menos 8 problemas técnicos, indicando evidencia, ubicación, impacto, riesgo y prioridad de corrección.
4. **Aplicación de SOLID y Clean Code:** mejora de responsabilidades, nombres, funciones, manejo de errores, cohesión, acoplamiento y límites entre componentes.
5. **Refactoring seguro:** aplicación documentada de al menos 4 refactorings, incluyendo Extract Method, Move Method o reubicación de responsabilidad, e Introduce Parameter Object o simplificación equivalente.
6. **Pruebas y verificación:** definición de casos de prueba o evidencias antes/después que permitan comprobar que no se alteró negativamente el comportamiento externo.
7. **Code review profesional:** elaboración y aplicación de un checklist técnico con observaciones, feedback objetivo, correcciones y criterios de aceptación.
8. **Conclusiones:** aprendizajes, dificultades, límites del trabajo y mejoras futuras.

### 📊 Modelo orientativo de presentación del TPI

Este apartado ofrece una **guía visual y conceptual** para orientar la presentación del Trabajo Práctico Integrador de **Metodología de Sistemas II**. No reemplaza la consigna oficial ni constituye un formato único obligatorio, sino que funciona como una referencia para ordenar el trabajo, comunicar decisiones técnicas y defender el proceso realizado.

####   

#### 🎯 Finalidad del modelo

La presentación debe ayudar a explicar, de manera clara y profesional, cómo el equipo analizó un sistema o módulo, identificó problemas de calidad interna, reconoció deuda técnica y aplicó criterios de mejora basados en **SOLID, Clean Code, refactoring seguro, pruebas y code review**.

**Importante:** el modelo es orientativo. Cada equipo debe adaptarlo a su caso real, justificar sus propias decisiones y evitar copiarlo de manera literal.

####    

#### 🧩 Estructura sugerida de la presentación

1. **Portada**\
   Nombre del trabajo, materia, comisión, integrantes, docente y fecha.
2. **Resumen ejecutivo**\
   Breve síntesis del sistema analizado, problema principal, mejoras aplicadas y conclusión técnica.
3. **Descripción del caso**\
   Presentar el sistema o módulo seleccionado, sus usuarios principales, alcance y funcionalidades observadas.
4. **Calidad externa vs. calidad interna**\
   Diferenciar qué funciona correctamente desde la mirada del usuario y qué problemas aparecen en la estructura interna del código.
5. **Deuda técnica y mantenibilidad**\
   Explicar qué decisiones o problemas técnicos dificultan la evolución futura del sistema.
6. **Code smells detectados**\
   Identificar señales de mal diseño: métodos extensos, duplicación, baja cohesión, alto acoplamiento o clases con demasiadas responsabilidades.
7. **Aplicación de SOLID y Clean Code**\
   Justificar cómo los principios y buenas prácticas permiten mejorar la estructura del sistema.
8. **Refactoring seguro**\
   Mostrar transformaciones realizadas o propuestas, como Extract Method, Move Method o Introduce Parameter Object, indicando que no se altera el comportamiento externo.
9. **Pruebas y validación**\
   Presentar evidencias de que el sistema mantiene su comportamiento luego de los cambios.
10. **Code review y conclusiones**\
    Incluir observaciones del equipo, checklist técnico utilizado, aprendizajes y próximos pasos.



#### 📌 Criterio recomendado para armar las diapositivas

**1. Diagnóstico**

Mostrar qué problemas se encontraron y por qué afectan la mantenibilidad.

**2. Mejora**

Explicar qué principios, técnicas o refactorings se aplicaron.

**3. Verificación**

Evidenciar que la mejora no rompió el comportamiento esperado.

**4. Reflexión**

Relacionar lo realizado con los contenidos de la asignatura.

####           

#### ✅ Recomendaciones para los estudiantes

- Evitar diapositivas saturadas de texto.
- Usar capturas, tablas o fragmentos de código solo cuando ayuden a explicar una decisión técnica.
- Mostrar ejemplos concretos de problemas detectados y mejoras propuestas.
- Relacionar cada mejora con un concepto de la materia.
- Cuidar la coherencia entre diagnóstico, refactoring, pruebas y conclusiones.
- No presentar únicamente definiciones teóricas: se espera aplicación sobre un caso concreto.
